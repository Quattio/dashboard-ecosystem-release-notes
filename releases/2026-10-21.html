        Predictive heating (MPC) — continued pilot development 5 tickets

        Model Predictive Control for central heating: cloud-trained house models that let the controller plan ahead. This wave extends the predictive-heating engine on the controller and in the message spec. It remains a pilot-cohort capability and does not change how any customer’s system heats today.

        • Predictive heating now uses an external weather forecast as a model input, with the forecast output added to the message spec (QPD-14948 Systems Control)
        • Solve the condensed mixed-integer problem with the DAQP solver (QPD-16248 Systems Control); low-level split of the boiler / heat-pump thermal power (QPD-15946 Systems Control)
        • Keep tracking the predictive-heating state while the MPC is off or the room temperature drops out (QPD-16182 Systems Control)
        • The state estimator resumes after a controller restart, with the estimator schema persisted and extended in the message spec (QPD-16100 Systems Control)
        Shipped but not live: predictive heating is not enabled for the fleet. It stays limited to the pilot cohort and does not change how any customer’s system heats today.
        Impact for CS: no customer-visible change and no field action.

        Service Tool and on-device service access point 2 tickets

        A new on-CiC field-service application ships for the first time in this alpha. cic-service-tool serves a web interface (EN/NL, credential login) that a technician reaches over a local service Wi-Fi access point managed by the new cic-access-point app. It is meant to streamline service, maintenance and new installations.

        • New cic-service-tool and cic-access-point apps added to the image: web UI with a system overview, per-device pages (heat pump / All-E, Chill, HeatCharger, boiler, thermostat) with live values and history, a Wi-Fi page, a Thread topology page, and a safety-timed manual mode that pauses the controller and releases control when the session ends (Embedded Systems)
        • The service access point CIC-<id>-service is opened by a 5-second button long-press and closes automatically after 60 minutes; its state drives the CiC LED (Embedded Systems)
        • Message-spec fields added for cic-service-tool and cic-access-tool (QPD-15839 Embedded Systems)
        Impact for field service / installers: a new local service interface exists on the CiC in this build, reached over a service Wi-Fi access point. It is new in this alpha and is for service and installation use, not a customer feature. Do not present it to customers.

        ODU V2 and control robustness 4 tickets

        Controller robustness and ODU V2 handling: safer behaviour when components disconnect, and corrected ODU V2 simulation/mapping used in testing.

        • The controller handles null signals when components disconnect, instead of acting on missing values (QPD-15444 Systems Control)
        • Update the ODU V2 compressor frequency mapping, and report PCB firmware below 2.0 for a simulated ODU V2 (QPD-16159 Systems Control)
        • Adjust the central-heating maximum water-temperature range and keep the pump running at the limit (control-tuning change; no customer-perceivable comfort change claimed) (Systems Control)
        Impact for ops: internal robustness and test-rig correctness. No field action; the water-temperature range change is control tuning, not a customer-visible setting.

        Connectivity — Thread / CoAP 1 ticket

        Reliability of the CiC-to-dongle Thread mesh. Stale service advertisements could keep the CiC retrying against sessions that no longer exist.

        • Ignore expired SRP services and keep the CoAP restart backoff, so the CiC stops exhausting retries against dead sessions and avoids connection storms (QPD-16298 Embedded Systems)
        Impact for CS: fewer rare connection drop-outs between the CiC and its wireless accessories. This is the fix summarised generically on the Customer tab.

        Telemetry and message specification 6 tickets

        Telemetry plumbing and message-spec maintenance: cleaner cloud payloads, a stats-publishing fallback fix, and stricter enum typing.

        • Publish the device dew-point pair (QPD-14757 Embedded Systems)
        • When gzip fails, publish the uncompressed stats to cicStats, not cicZipStats (whose rule only parses gzip), so stats are not lost on a compression failure (QPD-16254 Embedded Systems)
        • Make commissioning mode and heat-pump test level proper enumerations; generate every custom cloud-data-type enum member (Embedded Systems)
        • Restore debug logging for the modem IMSI; stop sending unused telemetry fields to the cloud (Embedded Systems)
        Impact for ops: leaner and more robust telemetry. Modem-IMSI debug logging is available again; a forced-gzip-failure case no longer drops stats.

        Persistence, config and test infrastructure 3 tickets

        Robustness of how on-device configuration and message-spec data are persisted, plus test-harness fixes.

        • The controller-manager persists message-spec JSON keys to their own file (QPD-16161 Embedded Systems), and the message spec validates where persisted rows live (QPD-16198 Embedded Systems)
        • Test harness: keep ssh_cmd output that arrives with or after the exit status (QPD-16288 Embedded Systems)
        Impact for ops: internal persistence and test robustness. No field action.
